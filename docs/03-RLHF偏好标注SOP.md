# RLHF 偏好标注 SOP

目标：产出**人与人一致、与自己一致**的偏好数据。偏好标注最大的敌人是"今天喜欢长的，明天喜欢短的"。

## 1. 任务形态

- **成对**（最常见）：prompt + response_A + response_B → 选 A / B / 平
- **列表**：prompt + N 个回复 → 全排序
- **打分**：单回复按维度打分（更接近评测，见 docs/01）

本 SOP 以成对为主，列表排序可拆成两两比较后合成。

## 2. 判断顺序（不要反）

1. **安全**：哪个更不安全，直接输，不用比文采
2. **事实**：谁有硬事实错误，直接输
3. **指令遵循**：谁漏了必须项（字数/格式/要点）
4. **有用性**：谁更解决问题
5. **表达**：最后才看流畅、风格

前三步能定胜负就不要进入第四步。**"写得舒服"不能盖过"答非所问"**。

## 3. 平局的使用

平局是稀缺资源，只在两种情况给：
- 两个回复在安全/事实/遵循/有用性上**都**等价，表达差异不影响任务完成
- 两个回复**同样不可用**（都跑题 / 都拒绝了一个合法问题）

不允许因为"各有千秋"就平局——那是没拆维度的偷懒。

## 4. 理由怎么写

每个选择必须有一句**可检验**的理由：

```
差：A 更好，因为质量更高。
好：A 更好。指令要求"不超过 100 字且含报价"，A 88 字含报价 199 元；
    B 240 字且未报价，指令遵循失败。
```

理由里至少出现：**指令中的某个具体要求** 或 **某个事实点** 或 **某个安全点**。

## 5. 位置偏差与长度偏差

- 平台若随机 A/B，标注时**先遮住 A/B 标签看内容**再选
- 长回复不自动加分；超长且注水按"有用性"扣
- 连续 10 条都选同一位（都是 A 或都是 B）要停下来检查是不是没读题

## 6. 一致性自检

每 50 条做一次自复查：从已标里抽 5 条隔天重标，不一致率 > 15% 说明标尺漂了，回去重读 SOP 并找组长校准。

## 7. 交付格式

```json
{
  "id": "rlhf-001",
  "prompt": "……",
  "A": "……",
  "B": "……",
  "choice": "A",
  "rationale": "……",
  "dimensions": {
    "safety": "tie",
    "fact": "A",
    "instruction": "A",
    "helpfulness": "A"
  }
}
```

`choice` 必须与 `dimensions` 的多数派一致，除非安全/事实一票定输赢——此时在 rationale 里写明"一票否决"。
